# Virtual Memory

## Introduction

Traditionally, memory management requires entire processes to be loaded into main memory for multiprogramming. **Virtual Memory**, however, allows processes to execute without being completely loaded, offering several key advantages:

*   The logical address space can be larger than available physical memory.
*   It enables efficient sharing of files, libraries, and shared memory.
*   It facilitates faster process creation.

While physical memory constraints inherently limit program size to available RAM, loading an entire program is often unnecessary. A significant portion of a program may remain unused (e.g., rarely accessed error handling code, over-allocated data structures, or optional features).

Partial loading of programs into memory therefore provides significant benefits:
*   It allows programs larger than physical memory to run.
*   It increases multiprogramming by reducing each program's physical memory footprint, thereby improving CPU utilization and overall system throughput.
*   It reduces the I/O needed for loading or swapping segments, which leads to faster program startup and execution.

## Virtual Memory Concepts

Virtual memory fundamentally separates the user's logical view of memory from the underlying physical memory.

### Virtual Address Space

The **Virtual Address Space** represents a process's logical view of its memory organization. Processes typically perceive memory as a single, contiguous block of addresses. In contrast, physical memory is organized into non-contiguous, fixed-size **frames**. The **Memory Management Unit (MMU)** is responsible for translating these logical addresses generated by the CPU into physical addresses.

A common logical address space layout typically includes:
*   **Code (Text):** Residing at low addresses.
*   **Initialized Data:** Following the code section.
*   **Uninitialized Data (BSS):** Placed after initialized data.
*   **Heap:** Grows upwards for dynamic memory allocation.
*   **Stack:** Grows downwards from high addresses for function calls and local variables.

The space between the Heap and Stack is left free to allow for their respective growth.

Virtual memory further enables efficient sharing by mapping different processes' logical addresses for shared libraries or memory regions to the same physical frames.

## Implementation of Virtual Memory

Virtual memory is typically implemented using **Demand Paging**, which is the most common approach, or less frequently, Demand Segmentation.

### Demand Paging

**Demand Paging** operates as a "lazy" approach: it loads a page from secondary storage (backing store) into a physical memory frame *only when* the CPU first accesses an address within that specific page. This strategy effectively saves both I/O time and RAM for pages that remain unaccessed.

**Distinguishing In-Memory vs. On-Disk Pages: The Valid-Invalid Bit**
Hardware support is essential for demand paging, typically in the form of a **valid-invalid bit** within each page table entry:
*   **Valid (v):** Indicates the page is currently in a physical memory frame, and the entry contains its corresponding frame number.
*   **Invalid (i):** Signifies that the page is either not part of the process's address space (implying an illegal access) or is valid but currently resides on the backing store.

**Handling a Page Fault:**
If the CPU attempts to access a page marked "invalid," the MMU triggers a **page fault** exception, interrupting the CPU and transferring control to the OS. The OS page fault handler then performs the following steps:
1.  It first verifies if the access was directed to a valid logical address range. If the access is deemed illegal, the process is terminated.
2.  If the access is valid but the page is not in memory, the OS locates the page on the backing store.
3.  Next, it obtains a free physical memory frame. (If no frames are available, a page replacement algorithm is invoked to select a victim frame).
4.  The OS then issues a disk I/O request to read the required page into the allocated frame.
5.  It updates the process's page table entry for the newly loaded page (setting the valid bit and storing the frame number).
6.  Finally, the OS restarts the instruction that initially caused the page fault.

During the inherently slow disk I/O operation, the OS can perform a **context switch**, allowing another ready process to utilize the CPU.

**Worst Case of Demand Paging: Pure Demand Paging**
Starting a process with none of its pages pre-loaded can lead to immediate and subsequent page faults for every new page access, resulting in extremely slow startup times. Consequently, real systems employ optimizations such as *pre-paging*.

### Free-Frame List

The OS maintains a **free-frame list**, which is a collection of available physical memory blocks. When a frame is needed, it is allocated from this list. For security purposes, the OS often **zeros out** a frame before allocating it to a process. If the free-frame list becomes empty, page replacement mechanisms become necessary.

### Performance of Demand Paging

The **Effective Access Time (EAT)** for memory in a demand-paged system is calculated using the following formula:
$$ EAT = (1 - p) \times ma + p \times t_{pf} $$
Where:
*   $ma$: Represents the memory access time (e.g., 200 ns).
*   $p$: Denotes the probability of a page fault (also known as the page fault rate).
*   $t_{pf}$: Is the average page fault service time (e.g., 8 ms = 8,000,000 ns), which is predominantly determined by disk I/O.

Example: If $ma = 200$ ns and $t_{pf} = 8,000,000$ ns.
$$ EAT = 200 + 7,999,800 \times p \quad (\text{in ns}) $$
*   If $p = 0.001$ (meaning 1 in 1,000 accesses results in a fault), $EAT \approx 8200$ ns, which is 41 times slower than a direct memory access ($ma$).
*   To maintain performance degradation below 10% (i.e., $EAT < 220$ ns), $p$ must be less than approximately $0.0000025$, signifying fewer than 1 page fault per 400,000 memory accesses.

**Conclusion:** Therefore, an extremely low page fault rate is absolutely crucial for achieving acceptable performance in a demand paging system.

### Copy-on-Write (COW)

**Copy-on-Write** is an optimization for the `fork()` system call that effectively leverages virtual memory.
Traditionally, `fork()` involves duplicating the parent process's entire address space, which is an inherently slow operation. COW addresses this inefficiency as follows:
1.  **Share Pages Initially:** Both parent and child processes initially share the same physical frames, which are marked as "copy-on-write."
2.  **Trap on Write:** If either process attempts to write to a shared COW page, a page fault occurs.
3.  **Copy the Page:** The OS responds by allocating a new frame, copying the original page's contents to it, and updating the faulting process's page table to point to this new private copy.
4.  **Perform Write:** The write operation then proceeds on the process's now-private copy of the page.

**Benefits:** This approach makes `fork()` faster (since only page tables are initially copied), and it conserves memory by only duplicating pages that are actually modified.

## Page Replacement

When a page fault occurs and there are no free frames available (indicating memory over-allocation), **Page Replacement** is necessary. An existing page in memory (referred to as the **victim frame**) is selected; its contents are written to the backing store if they have been modified, and the freed frame is then reused for the newly needed page.

### Basic Page Replacement Mechanism

When a page fault occurs and no free frames are available, the following steps are typically executed:
1.  A **page replacement algorithm** selects a **victim frame** containing page $P_{victim}$.
2.  $P_{victim}$ is written to the backing store **only if it has been modified** (a check performed using the **dirty bit**).
3.  The page table entry for $P_{victim}$ is then updated (e.g., its valid-invalid bit is set to invalid).
4.  The new page ($P_{new}$) is read from the backing store into the now-free victim frame.
5.  The page table entry for $P_{new}$ is updated (its valid bit is set, and the frame number is stored).
6.  Finally, the faulting process resumes execution.

**The Dirty Bit (Modify Bit) Optimization:**
A **dirty bit** is associated with each page or frame and is automatically set to 1 by hardware whenever the page is written to. If the dirty bit is 0 (indicating the page is clean), the page has not been modified, and its frame can be overwritten without a disk write, which significantly saves time. However, if the dirty bit is 1 (indicating the page is dirty), its contents must be written back to the backing store before the frame can be reused.

## Page and Frame Replacement Algorithms

When page replacement becomes necessary, the OS selects a victim frame by employing a **page replacement algorithm**. The primary objective of these algorithms is to minimize the occurrence of future page faults. Algorithms are typically evaluated by counting the number of page faults they incur when processing a given **reference string** (a sequence of page numbers accessed) for a fixed number of available frames.

Example Reference String: `7, 0, 1, 2, 0, 3, 0, 4, 2, 3, 0, 3, 2, 1, 2, 0, 1, 7, 0, 1`

### FIFO (First-In, First-Out) Algorithm

**Policy:** This algorithm replaces the page that has resided in memory the **longest**.
**Implementation:** It is typically implemented using a FIFO queue to track the page load order.
**Example (3 Frames, using the reference string):** This policy results in **15 page faults**.
**Inefficiency:** A notable inefficiency of FIFO is that it can inadvertently replace frequently used pages simply because they were loaded earliest, despite their active use.

### Belady's Anomaly (FIFO)

Belady's Anomaly is a peculiar phenomenon observed in some page replacement algorithms (like FIFO) where, paradoxically, *increasing* the number of allocated physical frames can, for certain reference strings, actually *increase* the total number of page faults.
Example: `1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5`
*   With 3 Frames: 9 Page Faults
*   With 4 Frames: 10 Page Faults

### Optimal Algorithm (OPT or MIN)

**Policy:** The Optimal Algorithm replaces the page that **will not be used for the longest period of time in the future**.
**Guarantee:** It is guaranteed to achieve the **lowest possible page fault rate**.
**Impracticality:** This algorithm is inherently impractical for real-world implementation because it requires impossible knowledge of future page references.
**Usage:** Despite its impracticality, it serves as a theoretical benchmark for evaluating other page replacement algorithms.
**Example (3 Frames, using the reference string):** This algorithm results in **9 page faults**.

### Least Recently Used (LRU) Algorithm

**Policy:** The Least Recently Used (LRU) algorithm replaces the page that has **not been used for the longest period of time** (based on past usage). It fundamentally relies on the principle of *temporal locality*.
**Example (3 Frames, using the reference string):** This algorithm results in **12 page faults**.
LRU generally performs well in practice and, importantly, does *not* suffer from Belady's Anomaly.

**LRU Implementation Approaches (Expensive):**
1.  **Counters:** This approach requires hardware to update a "time-of-use" counter for every page on every memory access. During replacement, the OS must then scan all page table entries to find the page with the smallest counter value.
2.  **Stack:** This method maintains a stack (often implemented as a doubly linked list) of page numbers. On each page reference, the accessed page is moved to the top of the stack. The page at the bottom of the stack is then the LRU page. However, this still incurs significant overhead per memory access.

### LRU Approximation Algorithms

Due to the computational cost associated with true LRU implementations, operating systems typically employ various approximation algorithms, often utilizing the **Reference Bit**:
*   **Hardware sets:** The hardware automatically sets a reference bit (R) to 1 whenever a page is accessed.
*   **OS periodically resets:** The OS periodically reads the value of the reference bit and then resets it to 0.

This mechanism allows the OS to determine which pages have been used since the last reset, thereby distinguishing pages that were "used recently" from those that were "not used recently."

### Second-Chance (Clock) Algorithm

The Second-Chance (Clock) algorithm is an improvement over the basic FIFO algorithm, incorporating the reference bit.
**Structure:** Pages currently in memory are logically arranged in a circular list, with a "clock hand" pointer indicating the next page to consider for replacement.
**Policy:** When a page replacement is needed, the OS examines the page currently pointed to by the clock hand:
*   If its reference bit (R) is 0: This page is selected as the victim. The clock hand is then advanced.
*   If its R is 1: The page is given a "second chance." Its R bit is reset to 0, and the clock hand is advanced to the next page.

This process repeats until a page with R=0 is found. If the clock hand makes a full circle, it means all pages initially had R=1. In this scenario, all R bits are reset to 0 during the first pass, and the algorithm effectively behaves like FIFO on the second pass, replacing the first page it encounters.

### Enhanced Second-Chance Algorithm

The Enhanced Second-Chance algorithm takes into account both the **Reference bit (R)** and the **Dirty bit (M)**.
**Page Classes (Ordered by preference for replacement, from most desirable to least):**
1.  **(R=0, M=0):** Not recently used, Clean. This is the best candidate for replacement as it requires no disk write.
2.  **(R=0, M=1):** Not recently used, Modified. A good candidate, but requires a disk write before replacement.
3.  **(R=1, M=0):** Recently used, Clean. Less desirable for replacement, as it's active but doesn't require a write.
4.  **(R=1, M=1):** Recently used, Modified. The worst candidate for replacement, as it's both active and requires a disk write.

**Policy:** The algorithm scans the circular list in multiple passes, prioritizing the lower-numbered classes. During scans for (0,1) or higher-numbered classes, it simultaneously resets the R-bits of any (1,x) pages encountered.

### Counting-Based Algorithms

*   **Least Frequently Used (LFU):** This algorithm replaces the page that has the smallest reference count.
*   **Most Frequently Used (MFU):** Conversely, this algorithm replaces the page with the largest reference count.

However, these counting-based algorithms are less common in practice due to the high overhead associated with maintaining their reference counts.

### Page-Buffering Algorithms

Operating systems often proactively maintain a pool of free frames using page-buffering algorithms.
**Strategy:** When a page fault occurs and a victim page is chosen, the desired new page is immediately read into a frame taken from this free pool. This allows the faulting process to resume quickly. The victim page (if dirty) is then written back to disk asynchronously by a background process, and its frame is subsequently added back to the free pool.
**Benefit:** This approach effectively decouples the (potentially slow) page-in operation from the page-out operation, thereby significantly improving system responsiveness.

## Frame Allocation: How Many Frames per Process?

The operating system is responsible for deciding how many physical frames to allocate to each process.
*   **Minimum Number of Frames:** This quantity is determined by the CPU architecture and must be sufficient to hold all pages required for a single instruction to execute without immediately causing a page fault.
*   **Maximum Number of Frames:** This is limited by the total available physical memory in the system (excluding memory reserved for the OS itself).

### Frame Allocation Schemes

1.  **Equal Allocation:**
    *   **Policy:** Divides the total available frames ($m$) equally among $n$ processes, assigning $m/n$ frames to each.
    *   **Drawback:** This scheme ignores the varying sizes and memory needs of different processes.

2.  **Proportional Allocation:**
    *   **Policy:** Allocates frames proportionally to each process's size ($S_i$).
    *   **Formula:** $a_i = (S_i / S) \times m$, where $S = \sum S_i$ represents the total size of all processes.
    *   **Advantage:** This approach is generally more sensible than equal allocation.
    *   **Priority Consideration:** It can be further modified to incorporate process priority.
    *   **Dynamic Changes:** The allocation may require recalculation if the degree of multiprogramming changes.

## Global vs. Local Page Replacement

When a page fault occurs, the victim frame can be chosen from two different scopes:

1.  **Global Replacement:**
    *   **Policy:** The page replacement algorithm selects a victim frame from the **entire set of frames** available in the system (excluding those critical to the OS).
    *   **Implication:** A page fault originating from one process can cause a frame belonging to another process to be replaced. Consequently, the number of frames allocated per process can fluctuate dynamically.
    *   **Pros:** This approach often leads to higher overall system throughput.
    *   **Cons:** It results in less predictable per-process performance, and a single misbehaving process can potentially impact the performance of others.

2.  **Local Replacement:**
    *   **Policy:** The page replacement algorithm chooses a victim frame **only from the frames currently allocated to the faulting process**.
    *   **Implication:** Under this policy, the number of frames assigned to each process remains constant.
    *   **Pros:** It provides more predictable performance for individual processes and helps isolate processes from each other.
    *   **Cons:** It can be less globally efficient, as a low-priority process might hoard unused frames that could otherwise benefit other processes.

### Page Reclaiming (Example Global Strategy)

Often employed with global replacement, a background OS process (known as a page daemon or reaper) proactively maintains a pool of free frames.
*   **Thresholds:** This process operates using a **low watermark** and a **high watermark** for the size of the free-frame list.
*   **Operation:** When the number of free frames drops below the low watermark, the reaper scans memory (e.g., using a Clock-like algorithm), identifies candidate victim pages (e.g., those not recently used), reclaims them (writing dirty pages to disk), and adds their frames to the free list until the high watermark is reached.
*   **Goal:** The primary goal is to ensure a sufficient number of free frames are consistently available for quick page fault service, while offloading the writing of dirty pages to disk to a background process.

## Non-Uniform Memory Access (NUMA)

In larger multi-processor systems, **NUMA** architectures are prevalent. In these systems, physical memory is divided into nodes, and "local" memory (memory within the same node as a CPU core) is significantly faster to access for specific CPU cores than "remote" memory (memory in other nodes).
**Implications for Memory Management:**
*   **Frame Allocation:** The OS should endeavor to allocate frames for a process on the local memory node of the CPU core where that process is currently running.
*   **Page Replacement:** Page replacement algorithms might be designed to prefer replacing pages located on remote nodes.
*   **Process/Thread Scheduling:** The scheduler attempts to keep threads running on CPU cores within the same memory node as their associated memory, thereby minimizing slow remote accesses.

NUMA architectures therefore introduce significant additional complexity to operating system memory management.

## Thrashing and the Locality Model

**Thrashing:** This describes a detrimental state where a process or the entire system spends an excessive amount of time performing paging operations (swapping pages in and out) rather than executing useful computation.
**Cause:** Thrashing typically occurs when a process is not allocated enough physical frames to hold its **working set** (the set of pages it actively uses).
**Symptoms:** Key indicators include extremely high page fault rates, constant disk I/O, and very low CPU utilization.
**The Thrashing Cycle:** This destructive cycle begins when low CPU utilization mistakenly prompts the OS to increase the degree of multiprogramming. This leads to processes competing for and stealing frames from one another, resulting in an even higher page fault rate, further drops in CPU utilization, and ultimately, system collapse.

### Demand Paging and Thrashing Prevention

*   While local replacement can contain thrashing to a single process, it does not fundamentally solve the underlying problem.
*   **Key Solution:** The crucial solution is to ensure that each process is allocated enough frames to accommodate its current working set. This approach fundamentally relies on the **Locality Model**.

### The Locality Model

*   **Principle of Locality:** This fundamental principle states that programs exhibit *temporal locality* (items referenced recently are likely to be referenced again soon) and *spatial locality* (addresses near recently referenced ones are likely to be referenced soon).
*   **Locality / Working Set:** During its execution, a process typically accesses only a small subset of its pages. This subset constitutes its current **locality** or **working set**.
*   **Impact:** If a process is allocated enough frames to contain its working set, it can run efficiently. Conversely, if it lacks sufficient frames, it will constantly incur page faults, leading to thrashing.

### The Working-Set Model (WS)

The Working-Set Model provides a formal framework for estimating a process's current locality.
*   **Working-Set Window ($\Delta$):** This is a parameter that defines a recent activity interval (e.g., the last $\Delta$ page references).
*   **Working Set ($WS(t, \Delta)$):** This is defined as the set of distinct pages referenced by a process within the time interval $[t - \Delta, t]$. It serves as an estimate of the process's current locality.
*   **Working Set Size ($WSS_i(\Delta)$):** This is the number of pages within the working set for process $P_i$, a value that changes dynamically during execution.

**Using the Working-Set Model for Thrashing Control:**
1.  The OS estimates $WSS_i(\Delta)$ for each active process.
2.  It then calculates the total demand for frames: $D = \sum WSS_i(\Delta)$.
3.  Finally, it compares this total demand $D$ to the total available frames ($m$):
    *   If $D \le m$: There is sufficient memory. The OS allocates at least $WSS_i(\Delta)$ frames to each process. If $m > D$, more processes can potentially be admitted.
    *   If $D > m$: Memory is over-allocated, and there is a high risk of thrashing. In this situation, the OS must **reduce the degree of multiprogramming** by suspending some processes and reclaiming their frames to meet the working set needs of the remaining active processes.

**Tracking the Working Set (Approximation):**
A common approximation for tracking the working set involves using the **reference bit** in conjunction with timer interrupts. At each interrupt, history bits for each page are shifted, the current reference bit's value is copied to the leftmost history bit, and the hardware reference bit is reset. A page is considered part of the working set if any of its history bits are set within the $\Delta$ window.

### Page-Fault Frequency (PFF) Control

Page-Fault Frequency (PFF) control is an alternative approach that monitors each process's **page fault rate** to dynamically adjust its frame allocation.
*   **Idea:** The core idea is to define acceptable upper and lower bounds for the PFF.
    *   If the PFF is too high: The process likely needs more frames.
    *   If the PFF is too low: The process might be allocated too many frames.

**Algorithm (Time-Between-Faults Variant):** This specific variant monitors the time $T$ between consecutive page faults for a process, comparing it against a predefined threshold $c$.
*   If $T < c$ (indicating a PFF that is too high): A new frame is allocated to the process.
*   If $T \ge c$ (indicating a low or acceptable PFF): The OS scans the process's allocated pages, removes any with a reference bit of 0 (meaning they are clean and not recently used), and then resets the reference bits of the remaining pages.

## Kernel Memory Allocation

The operating system kernel allocates memory for its internal data structures using strategies that differ from those employed for user process memory.
**Reasons for Separate Kernel Allocation:**
1.  **Variable and Small Sizes:** Kernel structures vary greatly in size, often being much smaller than a full page. This necessitates efficient allocation to avoid internal fragmentation.
2.  **No Paging (Often):** Critical kernel code and data are frequently "pinned" in physical memory and not paged out, a measure taken to prevent fatal system faults.
3.  **Need for Contiguous Memory:** Certain hardware components (e.g., those supporting Direct Memory Access, DMA) explicitly require physically contiguous blocks of memory.

Two common kernel memory allocation strategies are:

### Buddy System

**Concept:** The Buddy System allocates memory in **physically contiguous** blocks that are always **powers of 2** (e.g., 4KB, 8KB).
**Allocation Process:**
1.  The system maintains separate free lists for each power-of-2 block size.
2.  To satisfy a request of size `s`, the system rounds `s` up to the nearest power of 2 ($2^k$).
3.  If a block of size $2^k$ is not immediately available in the free list, the system recursively splits a larger available block ($2^j$, where $j>k$) into two "buddies" until a $2^k$ block is obtained.

**Fragmentation:** This system inherently suffers from **internal fragmentation** because it often allocates a larger power-of-2 block than the exact memory requested.
**Coalescing Advantage:** When a block is freed, the system efficiently checks if its "buddy" (the other half of the block it was split from) is also free. If both are free, they are merged back into a larger power-of-2 block. This merging process can propagate upwards, effectively reforming large contiguous free blocks.

### Slab Allocation

**Concept:** Slab allocation is a modern approach optimized for efficiently allocating many instances of the **same type of kernel object** (e.g., process descriptors).
**Components:**
*   **Cache:** A pool dedicated to objects of a specific type.
*   **Slab:** Consists of one or more **physically contiguous pages** that are allocated to a cache. These pages are pre-formatted to hold multiple instances of the specified object type.
*   **Object:** An actual instance of the kernel data structure.

**Allocation Process:**
1.  When a request for an object of type T is made, the system first looks within the relevant cache for a slab that has a free object slot.
2.  If no free objects are found within existing slabs, the system requests new contiguous pages (often from the Buddy System), formats them into a new slab, adds this new slab to the cache, and then allocates an object from it.

**Deallocation Process:** Objects are simply marked as free within their respective slabs, remaining available for quick reallocation. Slabs are returned to the general memory pool only if they become completely empty and the underlying memory is needed elsewhere.
**Advantages:**
*   **Speed:** Offers very fast allocation and deallocation by simply manipulating pointers within the pre-allocated slabs.
*   **No Internal Fragmentation (for objects):** Objects fit perfectly into their pre-carved slots within the slabs, eliminating internal fragmentation at the object level.
*   **Hardware Cache Locality:** By keeping objects of the same type together in slabs, this approach significantly improves CPU cache performance due to better data locality.

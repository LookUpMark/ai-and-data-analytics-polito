> [!summary] **Document Summary**
> How exceptional events are handled in pipelined processors, where several instructions are in flight at the same time. Distinguishes exceptions (internal CPU events) from interrupts (external I/O events), lists sources and the five classification axes, describes the steps for stopping and restarting execution (restartable machines), the 80x86 and ARM interrupt protocols, and the requirements of precise exceptions, their cost and the imprecise-exception problem with multicycle FP units. ## Exceptions vs. Interrupts

> [!definition] **Exception**
> An event that modifies the normal execution order of the program. In stricter usage, *exception* refers to an **internal CPU event** such as FP overflow, an MMU fault (e.g., page fault), or a trap (SWI).

> [!definition] **Interrupt**
> Usually an **external I/O event**, such as an I/O device request or reset.

The two terms are often confused; exceptional events (exceptions, interrupts, faults) are **more complex to handle in pipelined architectures** because several instructions are being executed at a time.

### Exception sources

- I/O device request
- Operating system call by a user program
- Tracing instruction execution
- Breakpoint (programmer-requested interrupt)
- Integer arithmetic overflow or underflow
- FP arithmetic anomaly
- Page fault
- Misaligned memory accesses
- Memory-protection violation
- Undefined instruction
- Hardware malfunction
- Power failure

## Exception Classification

| Axis | Alternatives |
|---|---|
| Synchronism | **synchronous** (always triggered at the same position in the code) vs. **asynchronous** (normally generated by external devices) |
| Request | **user requested** (similar to procedures) vs. **coerced** (out of control of the user program) |
| Maskability | **user maskable** vs. **user nonmaskable** (the user can force the hardware not to answer maskable requests) |
| Timing | **within** instructions (generated by the instruction itself) vs. **between** instructions |
| Behaviour | **resume** (execute something and then resume) vs. **terminate** |

## Stopping and Restarting Execution

> [!definition] **Restartable machine**
> A machine able to handle an exception, **save the state**, and **restart** without affecting the execution of the program. Nearly all processors nowadays are restartable.

When an exception occurs, the pipeline must:

1. force a **trap instruction** into the pipeline on the next IF;
2. until the trap is taken, **turn off all writes** for the faulty instruction and for all the following instructions in the pipeline;
3. when the exception handler receives control, it immediately **saves the PC of the faulty instruction**.

After the exception has been handled, special instructions **reload the PC and restart** the instruction stream.

### Interrupt protocol in 80x86

1. An external device sends an interrupt request.
2. CPU detects the interrupt.
3. The CPU reads the **Interrupt Type N** from the bus.
4. The CPU saves the **PSW** (processor status word) and the **return address** (Code Segment + Instruction Pointer) on the stack.
5. The CPU resets the interrupt flags, disabling external interrupts and trap mode.
6. Using N as index, the processor reads from the **Interrupt Vector Table** the address to jump to.
7. The CPU jumps to the **Interrupt Service Routine**.

### Interrupt protocol in ARM

1. An external device sends an interrupt request.
2. CPU detects the interrupt.
3. The CPU pushes onto the current stack a frame of **8 registers**, including the **Program Counter** and the **Processor Status Register**.
4. The CPU updates the processor flags and jumps to the address given by the interrupt type N; at that address a further jump to the actual **Interrupt Service Routine** may be placed.

The two protocols compared:

| Aspect | 80x86 | ARM |
|---|---|---|
| Vector lookup | interrupt type N read from the bus → index into the Interrupt Vector Table | jump to the address given by type N (a further jump to the ISR may be placed there) |
| State saving | PSW + return address (CS, IP) pushed on the stack by the CPU | 8-register stack frame including PC and PSR pushed by the CPU |
| After saving | interrupt flags reset (external interrupts and trap mode disabled) | processor flags updated |

## Precise Exceptions

> [!definition] **Precise exceptions**
> A processor has precise exceptions if the pipeline can be stopped so that:
> - the instructions **just before** the instruction that triggered the exception are **completed**;
> - the instructions **following** it can be **restarted from scratch**.

Restarting after an exception is very hard if exceptions are not precise; **precise exception handling is a must for most architectures, at least for integer instructions**.

**Cost**: some processors (Alpha 21064, MIPS R800 — *R8000*) implement precise exceptions in **debug mode only**, a mode about **10× slower** than normal.

## Imprecise Exceptions

Guaranteeing precise exceptions is more complex with multicycle instructions:

```asm
DIV.D F0, F2, F4      ; very long
ADD.D F10, F10, F8    ; completes before DIV.D
SUB.D F12, F12, F14   ; completes before DIV.D
```

ADD.D and SUB.D complete **before** DIV.D (out-of-order completion). If an exception arises during SUB.D, an **imprecise exception** occurs.

### Solutions

1. **Accept** imprecise exceptions.
2. Provide a **fast but imprecise** operating mode, and a **slow but precise** one (only one FP instruction executed at a time).
3. Force FP units to **determine early** whether an instruction can cause an exception, and issue further instructions only when previous ones are guaranteed not to cause exceptions.
4. **Buffer the results** of each instruction until all previously issued instructions have completed.

## Exceptions in the MIPS Pipeline

Possible sources of exceptions per stage:

| Stage | Cause of exception |
|---|---|
| IF | page fault on instruction fetch; misaligned memory access; memory-protection violation |
| ID | undefined or illegal opcode |
| EX | arithmetic exception |
| MEM | page fault on data fetch; misaligned memory access; memory-protection violation |
| WB | none |

### Contemporary exceptions

```
LD    ...        IF ID EX MEM WB
DADD  ...           IF ID EX  MEM WB
```

A **data page fault** can occur in the MEM stage of LD, and an **arithmetic exception** in the EX stage of DADD — both in the same cycle. The first exception is processed and, if its cause is removed, the second is handled.

### Exception ordering

Two exceptions can occur in the **opposite order** of the instructions they relate to: an instruction page fault on the *second* instruction (detected in IF) is raised **before** a data page fault on the *first* instruction (detected in MEM).

**Solution**: associate a **status flag** with each instruction in the pipeline:

- if an instruction causes an exception, its status flag is set;
- if the flag is set, the instruction cannot perform any **write** operation;
- when an instruction reaches the **last pipeline stage** and its flag is set, the exception is triggered.

This makes exceptions effectively precise (and ordered as the instructions).

## Instruction Set Complications

- **Early state changes**: an instruction is **committed** when it is guaranteed to complete. Some machines have instructions that change the state before they commit (e.g., **autoincrement addressing modes**). If such an instruction is aborted by an exception, the machine state is left altered → precise exceptions become very difficult. A possible solution is **rolling back** all state changes made by an instruction before it commits.
- **Implicitly updated condition codes** (as in the ARM instruction set):
  - they can cause **data hazards**;
  - they must be **saved and restored** on exceptions;
  - they make it harder for the compiler to fill delay slots between the instruction setting the flags and the branch.
- **Complex instructions** are difficult to pipeline; forcing them to fixed length is hardly achievable. Sometimes the problem is solved by **pipelining the microinstructions** that implement each instruction.
